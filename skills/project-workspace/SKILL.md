# Project Workspace

Treat the project, not the machine or chat, as the unit of work. The installed Skill does not establish a connection, grant credentials, enroll devices, or execute code. Discover live MCP tools and their authorization before starting.

1. **Resolve the project.** List projects and linked GitHub repositories. Retrieve relevant versioned notes and search project knowledge. Check prior workspaces, artifacts, and snapshots before repeating work. Never infer that a repository association grants GitHub write permissions.
2. **Choose the environment.** List environment definitions and their status. Select an approved, versioned environment matching the application/toolchain and CPU architecture. An environment is a *container image*; a workspace contains project files. Defining a Dockerfile does not install anything until `environment_build` reports completion. Proprietary software such as Vivado must be supplied by the authorized operator under its license. Never put license secrets or credentials in image layers.
3. **Reserve hardware deliberately.** Inspect `list_compute_nodes` and `list_hardware`. Request explicit GPU, NPU, or FPGA counts with `workspace_create(hardware={...})`. USB passthrough requires explicit operator permission, a user-selected worker and device ID, and `workspace_create(usb_passthrough=true, usb_node=..., usb_device_id=..., hardware={"usb":1})`. It is disabled by default. Never choose a USB target on the user's behalf or infer authorization to erase it; confirm device identity before any destructive flashing command. Treat inventory as advisory and only a confirmed workspace reservation as allocated. A missing device mapping is not permission to access host `/dev` paths. A compilation-only FPGA job need not reserve the physical board.
4. **Wait for a ready workspace.** `workspace_create` queues the start. Poll `workspace_list` until the selected workspace is ready; do not execute against a pending or failed lease. Use only its workspace-scoped operations. Node administration is a separate, explicitly authorized action.
5. **Checkout exact repository revisions.** Invoke `github_checkout_repository` only for linked repositories and wait for the import operation result. Record the exact resolved commit SHA. Repositories are placed under `/workspace/repos/OWNER__REPO`; they do not contain controller GitHub credentials.
6. **Execute and inspect.** Use `workspace_call` for commands, reads, writes, directory listings, and search. For large binary inputs (such as OS images), use the controller's authenticated streamed artifact-upload endpoint and `workspace_import_artifact`, then verify the checksum in the workspace before acting on hardware. Poll `workspace_operation` until its terminal result. A successful operation with `exit_code != 0` is a failed command. Use `expected_sha256` to prevent blind file overwrites, and record test outcomes rather than inferring success from queued tasks.
7. **Preserve distinct artifacts.** Save key output files with `export_file`; save the workspace file tree with `workspace_snapshot`, then verify its recorded artifact. Save the application/toolchain image independently with `environment_export`. Restore workspace files by choosing an authorized snapshot; load a saved image on another node with `environment_import`. Neither operation snapshots running process memory. Inspect artifact hashes and environment versions before relying on them.
8. **Publish and record.** Create a revision-guarded draft PR with `github_publish_artifacts` using the exact expected base SHA. Confirm provider evidence; never claim publication or merge based only on an enqueued request. Write project notes with `expected_version`, and reconcile conflicts. Separate proposals, measurements, and verified results.
9. **Release safely.** Request `workspace_destroy` and verify confirmed termination. Hardware reservations remain held when cleanup fails or the worker disappears. Do not represent an expired lease as a safely released GPU or FPGA. Do not delete worker volumes before the required snapshot has been retained.

The Go controller gateway handles project and versioned-note operations; Python remains the authoritative scheduler, GitHub broker and MCP backend during migration. The controller currently has a single privileged administrator identity. Never put the controller token, GitHub credentials, or host SSH keys inside worker command payloads, notes, snapshots, or image recipes. Do not treat the Docker runtime as a security boundary for adversarial multi-tenant code. Report untested hardware integrations as unverified.
